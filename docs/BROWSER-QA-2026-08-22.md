# Vectora — Browser QA, 2026-08-22

A full browser pass over `feat/help-center-assistant-dashboard` before deployment: every
route in both themes at desktop and mobile widths, every settings pane, the record detail
tabs, the help centre and the assistant — plus the three automated suites and the
artifacts that actually ship.

Instrumented for uncaught exceptions, console errors, failed requests and 4xx/5xx
responses; screenshots reviewed by eye in both themes. Chrome 151 headless via Playwright
1.62, against the vite dev server on `:8080` **and** the built bundle on `:8000`, because
the two differ in ways that have bitten this project before.

## Findings

- [x] **An organization's Deals tab showed contacts, or nothing at all.** `tabIndex` on
      both organization pages holds the tab's *name* (`'Deals'` / `'Contacts'`), but the
      `rows` computed tested it for falsiness — the idiom from when it was a numeric
      index. `!'Deals'` is always false, so `rows` always read the contacts resource and
      always mapped it through `getContactRowObject`, while `columns` directly beside it
      compared the string correctly and returned the deal columns. Two failure modes
      followed. An organization with deals but no contacts reported **"No Deals yet"**,
      because the empty-state test is `rows.length` and rows were the empty contacts list
      — a seeded org with seven deals showed the empty state. An organization *with*
      contacts rendered contact rows under deal headers, and `DealsListView` threw on the
      first deal-only column (`item.label` on an undefined `item`), leaving the tab blank.
      Fixed by comparing the name, as `columns` already does, in `pages/Organization.vue`
      and `pages/MobileOrganization.vue`. The rest of the codebase was swept for the same
      shape: `Lead`, `Deal`, `Activities` and the mobile pages all compare tab values
      correctly, and `FieldLayoutEditor` uses a genuine numeric index. `eec8d7fd`

- [x] **81 button icons rendered nothing.** `FeatherIcon` back-compat was removed in
      frappe-ui 1.0 (ADR-0008): an icon prop now takes a `lucide-*` string or a component,
      and `src/utils/iconString.ts` is explicit that a bare name like `trash-2` "renders
      nothing". 81 literal call sites across 34 files still passed bare names. It stayed
      invisible because `warnUnsupportedIconString` dedups on `${component}.${prop}` — one
      line covers every `Button.icon` in the app — and returns early under
      `import.meta.env.PROD`, so a production build says nothing at all. Two console lines
      stood for 81 sites. Measured, not inferred: Settings → Users' "New" button rendered
      `<!----><span class="truncate">New</span><!---->` with zero icon nodes, and the
      dashboard's date-range button had neither its calendar nor its chevron where both
      its neighbours had one each. Every literal name is now `lucide-*`; all 29 distinct
      names were checked against the pinned `lucide-static` set before conversion, since
      "not currently generated by Tailwind" and "not a real lucide icon" look identical
      from the browser. Bound props (`:icon="EditIcon"`) already passed components and
      were left alone. `9d85dae7`

- [x] **Warning badges rendered grey, or below the contrast floor.** Fifteen "Not Saved"
      badges, an onboarding progress badge and a "Beta" tag all ask for a warning tone and
      none of them got one. Thirteen passed `theme="amber"`, which renders — but
      `text-ink-amber-7` on `bg-surface-amber-2` measures **3.55:1** on a light surface,
      under the 4.5:1 AA floor for text that size. This is exactly the case `AGENTS.md`
      describes when it says to use orange and not amber. The other three passed
      `theme="orange"`, which frappe-ui's `Badge` does not support: `resolvePropValue`
      degrades it to grey, and the warning that says so is dev-only. The first pass caught
      only the three grey ones — the amber thirteen live inside dialogs and settings panes
      that a top-level page sweep never opens, which is why the contrast audit missed them
      too. All 17 now go through `components/ui/ToneBadge.vue`, which draws orange from
      the two tokens the dashboard and report notices already use
      (`bg-surface-orange-1` / `text-ink-orange-9`, **10.09:1** light and **11.88:1**
      dark) and passes every other tone straight through to `Badge` untouched. Drawing it
      rather than appending a class keeps it off the cascade: an appended
      `text-ink-orange-9` does win today, but only because the orange utility happens to
      be emitted after the grey one, which nothing tests and a dependency bump could
      reverse silently. Verified in situ at 10.09:1 on a real rendered badge, not only on
      the class string. Delete the orange branch when frappe-ui ships an orange theme; the
      call sites keep working. `0a3df903`

- [x] **Right-aligned dropdown menus opened left.** `placement` is removed and ignored in
      `Dropdown` in favour of `align`, so ten menus across eight files written as
      `placement="right"` were rendering against `align`'s default of `start` — on the
      opposite side from the one asked for. `Popover`, `Tooltip` and the date pickers
      still take `placement` and keep it. `9d85dae7`

- [x] **The telephony pane raised two 404s and an uncaught rejection on every visit.** A
      user who has never saved telephony settings has no `CRM Telephony Agent`, and
      `frappe.client.get` answers 404 for that — twice, once for the document and once for
      `get_doc_permissions`. The pane already handled it: its `onError` treated
      `DoesNotExistError` as "new document" and rendered correctly. It surfaced anyway,
      and the reason generalises beyond this pane: **frappe-ui's resource layer ends
      `handleError` with an unconditional `throw`**, so an `auto: true` fetch that fails
      rejects a promise nobody awaits no matter how completely the caller handled it. No
      `onError` the CRM can write suppresses that, which is why the request had to stop
      failing rather than be caught better. `frappe.client.get_value` answers `200` with
      `{}` for the same query, so the empty case arrives as data. The pane now makes one
      request instead of two, saves through `set_value` (or `insert` when there is no row
      yet), and keeps its editable document to the five fields it owns so a save sends
      only what the form can change. Both paths driven end to end: with no record the pane
      opens clean and Update creates the row; with a record present it loads the saved
      medium and Update writes through it. `5b03d2aa`

Also corrected in `9d85dae7`, both silent: `ViewControls` declared `loadMore`,
`resizeColumn` and `updatedPageCount` as `Boolean` when all three carry numbers — the
first two are change counters the list views increment, the third is the page length — so
every list view failed prop validation on mount; and the mobile header passed a class to
`CallUI`, which renders three root nodes and therefore drops it (the desktop header
passes none).

## Verified on the artifacts that actually deploy

- **No sourcemaps ship.** Zero `.map` files in the production output.
- **Both brand typefaces load.** All five referenced `woff2` files are emitted and return
  200; Space Grotesk and Inter resolve in the built page rather than falling back to
  `-apple-system`.
- **The production bundle renders every route** — 26/26 clean with no console warnings at
  all — and the e2e suite passes against it rather than against the dev server.
- **The assistant degrades gracefully.** A forced 500 and a forced network failure both
  produce "The assistant could not be reached right now… Try again", with no uncaught
  error. Its first answer after a cold start is slow (model warm-up), which is why an
  earlier reading of this looked like a hang.
- **No secrets tracked.** `deploy/.env` is gitignored and untracked; only the empty
  `.env.example` ships.
- **Compose config reviewed** — image tag required rather than defaulting to `stable`,
  secrets passed by environment rather than on the command line, resource ceilings on
  every service, healthchecks that traverse nginx to the backend, HTTP bound to loopback,
  and the scheduler explicitly enabled after site creation.

## What this pass did not cover

Being explicit, so none of this reads as verified:

- **One role only.** Everything ran as Administrator. Hierarchy scoping — what a rep sees
  versus a manager — is covered by the Python suite but was not exercised in the browser.
- **The compose stack was reviewed, not booted.** The findings on `deploy/` come from
  reading the configuration. No container was started, so first boot, upgrade and restore
  remain unverified here.
- **External integrations were not exercised.** Telephony, WhatsApp, ERPNext and lead
  syncing have no credentials on this site. Email send is covered by e2e against a muted
  mail queue.
- **The restored icons were spot-checked, not all 81.** Two were measured in the DOM
  before and after, and all 29 distinct names were confirmed present in the pinned lucide
  set — but each individual button was not opened and looked at.
- **Drag interactions were not driven.** Kanban reordering and the planner's
  drag-to-schedule were loaded and screenshotted, not dragged.
- **Two chunks dominate the bundle and were left alone.** `Dashboard` is 1.31 MB (432 KB
  gzipped) and `reportActionError` 937 KB (283 KB). Both are route-split and the app is
  responsive; they are the first candidates if load time on slow connections becomes a
  complaint, but splitting them is a change to make deliberately rather than inside a QA
  pass.
- **Calendar weekend shading tints Sunday only.** That is frappe-ui's documented default
  with no `weekendDays` configured — a vendored dependency in its own repository, so it
  was left alone. Set the config if Saturday should shade too.
- **Demo data shapes some screens.** The dev site carries e2e leftovers and seeded records
  — reps named `probe-`, repeated "Signal Test Org" suggestions. Those are site artifacts,
  not code defects.
